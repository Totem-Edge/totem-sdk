# OMN-115 — Factory persistence permits a stale record to overwrite a newer one

**Kind:** sdk-defect  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-factory`
**Observed versions:** @totemsdk/omnia-factory@0.9.0
**Origin:** Omnia adversarial audit — 26 November 2026 @ `c818f5e` (verified in source)

> reporter id OMN-113; fixed at the store boundary: saveFactory refuses a record whose currentSequence is below the stored sequence, while an equal-sequence replay stays idempotent
**Source:** `Omnia adversarial audit — 26 November 2026, reporter finding OMN-113 (omnia-factory/src/durable-factory-store.ts:83-88)`

## Context

saveFactory replaces the whole record without comparing the incoming sequence with the stored sequence. The storage CAS protects the write, not the semantic ordering of factory state.

## Impact

A delayed writer can roll a factory back to an older allocation or sequence.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-factory test
```

**Expected:** Writes are rejected when the incoming sequence is below the stored sequence.

**Actual:** Whole-record replace.

**Evidence:**

- durable-factory-store.ts:83-88

## Where to fix


### Approach

Enforce monotonic sequence at the store boundary and fail the write on regression.

## Constraints (do not violate)

- Do not require callers to pre-check the sequence.
- Keep recovery able to read older records.

## Acceptance criteria

- [ ] A stale save is rejected.
- [ ] Concurrent writers converge on the highest sequence.
