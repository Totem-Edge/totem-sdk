# OMN-045 — Recreating a VTXO pool with the same identity reset its capacity and commitment history

**Kind:** sdk-defect  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-host`, `@totemsdk/omnia-vtxo`
**Observed versions:** @totemsdk/omnia@3.0.0, @totemsdk/omnia-host@0.14.0, @totemsdk/omnia-factory@0.7.2, @totemsdk/omnia-vtxo@0.9.0, @totemsdk/omnia-pool@0.6.0, @totemsdk/liquidity-bond@0.4.0, @totemsdk/omnia-router@0.4.2, @totemsdk/omnia-splice@0.3.4, @totemsdk/chain-provider@0.4.0, @totemsdk/core@1.6.0
**Origin:** Totem Edge Omnia whole-family re-audit, 2026-11-17 @ `c81af31` (verified in source)
**Source:** `Deeper Omnia covenant/transaction audit, 2026-11-18 (verified against 51aed956)`

## Context

createVtxoPool unconditionally stored a freshly initialized pool under its deterministic id, so repeating the request reset available capacity, epoch and the membership set while earlier VTXOs stayed in the store. Creation is now create-only: an identical repeat returns the existing pool, and different terms are rejected.

## Impact

Capacity could be re-issued while orphaning the original membership history.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-host test
```

**Expected:** A repeated pool creation never resets capacity, epoch or members.

**Actual:** Fixed: the existing pool is returned (existed:true); conflicting terms are rejected.

**Evidence:**

- packages/omnia-host/src/api/methods.ts createVtxoPool
- packages/omnia-vtxo/src/commitment.ts computePoolId

## Where to fix

- `packages/omnia-host/src/api/methods.ts`

### Approach

Make creation create-only and idempotent for identical terms.

## Constraints (do not violate)

- Never reset capacity, epoch or members through the creation endpoint.

## Acceptance criteria

- [ ] A repeat returns the existing pool.
- [ ] Different terms are rejected.
- [ ] Capacity and members are unchanged.
