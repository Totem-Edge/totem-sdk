# OMN-032 — Pool accounting can diverge between liquidity positions

**Kind:** sdk-defect  
**Severity:** high  
**Status:** open  
**Packages:** `@totemsdk/omnia-host`, `@totemsdk/omnia-pool`
**Observed versions:** @totemsdk/omnia@3.0.0, @totemsdk/omnia-host@0.14.0, @totemsdk/omnia-factory@0.7.2, @totemsdk/omnia-splice@0.3.4, @totemsdk/omnia-vtxo@0.9.0, @totemsdk/omnia-pool@0.6.0, @totemsdk/liquidity-bond@0.4.0, @totemsdk/chain-provider@0.4.0
**Origin:** Totem Edge Omnia whole-family re-audit, 2026-11-17 @ `c81af31` (verified in source)
**Source:** `Deeper Omnia host audit, 2026-11-18 (verified against 41106016 / 997b7f4)`

## Context

The host stores a registry in the pool record and a copy in every position. Deposits update both, but allocation, release, withdrawal, approval and payout update only the position copy. Later deposits start from the older pool registry and can hold incompatible accounting versions at once.

## Impact

Divergent registry versions can misstate capital and may enable double payouts depending on the settlement backend.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-host test
```

**Expected:** A single authoritative, versioned pool registry drives every position mutation.

**Actual:** Mutations update position.registry only; pool.registry is stale after the first non-deposit mutation.

**Evidence:**

- packages/omnia-host/src/api/methods.ts pool mutation handlers (deposit/allocate/release/withdraw/approve/payout)

## Where to fix

- `packages/omnia-host/src/api/methods.ts`
- `packages/omnia-pool/src`

### Approach

Maintain one authoritative registry per pool, apply mutations through atomic versioned updates, and derive position views from it instead of copying.

## Constraints (do not violate)

- Do not silently fork a pool registry per position.

## Acceptance criteria

- [ ] A second deposit sees the latest allocation/withdraw state.
- [ ] Concurrent mutations fail on version conflict rather than overwrite.

## Verification (run before opening a PR)

