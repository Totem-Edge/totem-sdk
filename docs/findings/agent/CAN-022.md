# CAN-022 — Prepared operations bypass the channel lock; refunds are not surfaced by the host; journal is not cross-process safe

**Kind:** sdk-defect  
**Severity:** medium  
**Status:** open  
**Packages:** `@totemsdk/omnia-host`, `@totemsdk/omnia-router`, `@totemsdk/omnia-relay`
**Observed versions:** @totemsdk/omnia-host@0.13.4, @totemsdk/omnia-router@0.4.1, @totemsdk/omnia-relay@0.7.1
**Source:** `re-audit R-005, verified against source at 5d8c427b`

## Context

Three related gaps remain. (1) The shared lock keys on params.channelId, so prepared operations that identify the work by preparedOperationId do not take it (and multi-channel work has no ordered locking). (2) The router now returns pendingRefunds, but the host multi-hop method throws on failure instead of returning that recovery information, and nothing persists a refund queue. (3) The relay journal is a single document per process, but has no storage-level compare-and-swap and does not serialize by incoming HTLC identity.

## Impact

Concurrent prepared operations can interleave with RPC/peer mutations on the same channel; a failed multi-hop payment loses the refund schedule at the host boundary; two relay processes can lose a journal update.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-host test
```

**Expected:** Prepared, RPC and peer mutations share one lock; failures carry refunds; journal writes are atomic across processes.

**Actual:** Lock lookup ignores preparedOperationId; host throws the router result away; journal has no CAS.

**Evidence:**

- packages/omnia-host/src/api/methods.ts:3342-3358 — lock key derived only from params.channelId
- packages/omnia-router/src/execute.ts — pendingRefunds returned to the caller
- packages/omnia-host/src/api/methods.ts — multi-hop handler throws without surfacing pendingRefunds
- packages/omnia-relay/src/link-journal.ts — single document, no CAS or per-incoming-key lock

## Where to fix

- `packages/omnia-host/src/api/methods.ts`
- `packages/omnia-relay/src/link-journal.ts`

### Approach

Resolve the channel from the prepared operation before taking the lock; sort multi-channel locks by channelId to avoid deadlock; return pendingRefunds from the host multi-hop method and persist a refund queue; add a compare-and-swap to the journal (revision field) and an idempotency key on inChannelId+inHtlcId.

## Constraints (do not violate)

- Do not serialize unrelated channels.
- Do not report a failure as fully refunded.

## Acceptance criteria

- [ ] A prepared submission and an RPC call on one channel cannot interleave.
- [ ] Host multi-hop failures carry pendingRefunds and a scheduled retry.
- [ ] Concurrent journal writers cannot lose an update.
