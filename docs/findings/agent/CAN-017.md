# CAN-017 — Funding change goes to the first input owner, and the builder accepts negative output amounts

**Kind:** sdk-defect  
**Severity:** medium  
**Status:** in-progress  
**Packages:** `@totemsdk/omnia`, `@totemsdk/tx-builder`
**Observed versions:** @totemsdk/omnia@2.4.3, @totemsdk/tx-builder@0.3.2
**Source:** `security audit OMN-NEW-011, verified against source at 8fa26907`

## Context

The CAN-001 fix returns change correctly for a single-owner coin, but two edges remain. With several funding inputs, all excess value is sent to inputAddresses[0] even when the inputs belong to different addresses. In tx-builder, amounts are summed per token and checked against the inputs, but individual negative amounts are never rejected, so a negative output can offset a positive one and still balance.

## Impact

Multi-owner funding pays the change to the wrong party (and the transaction then cannot be signed by that party alone, so it fails late). The negative-amount gap means a draft can carry an invalid coin amount through conservation checking. Node acceptance of such a transaction was not demonstrated.

## Reproduce

```bash
pnpm --filter @totemsdk/tx-builder test
```

**Expected:** Change is returned per input owner, and every amount is required to be a non-negative integer before conservation is evaluated.

**Actual:** Change uses inputAddresses[0] unconditionally; sums() accepts BigInt("-100") and only compares totals.

**Evidence:**

- fix proposed in PR #218 (mixed-owner funding rejected; negative amounts refused)
- packages/omnia/src/transactions.ts:357 — const changeAddress = inputAddresses[0]
- packages/tx-builder/src/build.ts:119 — sums() parses amounts with BigInt without a sign check
- packages/tx-builder/src/build.ts:136 — only total > available is rejected

## Where to fix

- `packages/omnia/src/transactions.ts`
- `packages/tx-builder/src/build.ts`

### Approach

Require all funding inputs to share an owner before emitting change, or emit one change output per input address and reject mixed-owner funding with a clear error. In the builder, reject any amount that is negative or not an integer before summing.

## Constraints (do not violate)

- Keep the single-input exact-value path byte-identical.
- Do not weaken the existing conservation check.

## Acceptance criteria

- [ ] Mixed-owner funding either produces per-owner change or is rejected explicitly.
- [ ] An output with a negative amount is rejected by the builder.
- [ ] Offsetting positive and negative outputs cannot pass conservation.
