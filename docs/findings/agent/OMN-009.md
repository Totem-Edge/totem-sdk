# OMN-009 — EpochAuthority.append is check-then-act across an await

**Kind:** sdk-defect  
**Severity:** medium  
**Status:** open  
**Packages:** `@totemsdk/omnia-vtxo`
**Observed versions:** @totemsdk/omnia-vtxo@0.8.1
**Origin:** Totem Edge Omnia whole-family re-audit, 2026-11-17 @ `c81af31` (verified in source)
**Source:** `Omnia whole-family re-audit (2026-11-17), finding OMN-009`

## Context

append() reads current state, checks `spentInputIds`, then awaits `journal.append`. Two concurrent appends for the same input can both pass the check before either writes.

## Impact

The same VTXO input can be recorded in two epochs, defeating the double-spend guard the journal is meant to provide. Realistic only under concurrent callers in one process or two processes sharing the journal.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-vtxo test
```

**Expected:** Two concurrent appends of the same input: exactly one succeeds.

**Actual:** Both can pass the spent-input check before either append lands.

**Evidence:**

- packages/omnia-vtxo/src/epoch-authority.ts: `state.spentInputIds.has(inputId)` before `await this.journal.append(event)`

## Where to fix

- `packages/omnia-vtxo/src/epoch-authority.ts`

### Approach

Use an atomic reservation (compare-and-swap on the journal head, or a per-authority serial queue) so the spent set is advanced in the same durable step as the append.

## Constraints (do not violate)

- Do not add a process-local mutex as the only guard; two processes must still be safe.
- Preserve the existing signature and epoch ordering checks.

## Acceptance criteria

- [ ] Two concurrent appends of the same input: one wins, one throws.
- [ ] Reopen still shows a single record.
