# OMN-086 — An outgoing forward is journaled as active before the peer has received or acknowledged it

**Kind:** sdk-defect  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-relay`
**Observed versions:** @totemsdk/omnia-relay@0.10.0
**Origin:** Omnia SDK audit — 25 November 2026 @ `9f882c8` (verified in source)
**Source:** `Omnia SDK audit — 25 November 2026, reporter finding OMN-084`

## Context

After signing the outgoing HTLC the forwarder writes the link with status 'active', then connects to the peer and sends STATE_UPDATE. The journal does not retain the exact signed proposal or a deterministic message id, so a transport failure leaves an obligation recorded as active that the counterparty has never seen.

## Impact

Recovery cannot distinguish 'delivered and awaiting settlement' from 'never delivered'. The outgoing payment exists locally and may later be timed out on the intermediary's side, or be re-created with a different nonce, without any record of what the peer was actually offered.

## Reproduce

```bash
cd artifacts/canary && pnpm run canary run 38-omnia-relay-phase-a
```

**Expected:** The signed outgoing proposal is persisted with a deterministic message id and retransmitted until the peer acknowledges it.

**Actual:** The link is 'active' before connectToPeer/sendMessage, and neither the message nor an ack expectation is journaled.

**Evidence:**

- packages/omnia-relay/src/forwarder.ts:241 — record(intent) before signing
- packages/omnia-relay/src/forwarder.ts:245-262 — link 'active' written
- packages/omnia-relay/src/forwarder.ts:264-278 — connectToPeer and sendMessage afterwards

## Where to fix

- `packages/omnia-relay/src/forwarder.ts`
- `packages/omnia-relay/src/link-journal.ts`

### Approach

Journal the exact signed state update and a deterministic message id as a delivery obligation before sending. Move to 'active' only after the peer acknowledges. Add acknowledgement-based retransmission to the recovery pass.

## Constraints (do not violate)

- A link is not active until the peer has acknowledged it.
- Retransmission must reuse the same signed message; never re-sign a new one.
- Transport failure must leave a recoverable delivery obligation.

## Acceptance criteria

- [ ] A failed send leaves a pending-delivery record, not an active link.
- [ ] Recovery retransmits the identical signed proposal.
- [ ] A peer ack promotes the link to active exactly once.
