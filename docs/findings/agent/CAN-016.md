# CAN-016 — Relay link journal is not atomic and duplicate detection races the write

**Kind:** sdk-defect  
**Severity:** medium  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-relay`
**Observed versions:** @totemsdk/omnia-relay@0.7.1
**Source:** `security audit OMN-NEW-010, verified against source at 8fa26907`

## Context

record() writes the link, then reads the index, then writes the index as a separate operation with no transaction or compare-and-swap. Two concurrent forwards for the same hashlock both pass the duplicate check (which runs before record) and can then both record, with the second index write overwriting the first.

## Impact

A lost index update hides a link from list()-based recovery, and a duplicate forward creates two outgoing HTLCs for one incoming payment. Both are restart-sensitive and hard to see in logs.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-relay test
```

**Expected:** Journal writes are atomic and an incoming HTLC has a single idempotency key.

**Actual:** Two sequential storage.set calls per record; duplicate check precedes the write.

**Evidence:**

- fix proposed in PR #218 (single-document journal, serialized, upsert by hashlock)
- packages/omnia-relay/src/link-journal.ts:47 — storage.set(keyFor(hashlock), link)
- packages/omnia-relay/src/link-journal.ts:51 — storage.set(INDEX_KEY, index) (separate write)
- packages/omnia-relay/src/forwarder.ts:191 — duplicate check before addHTLC/record

## Where to fix

- `packages/omnia-relay/src/link-journal.ts`
- `packages/omnia-relay/src/forwarder.ts`

### Approach

Use one atomic write per link (store the index inside the record, or use a storage transaction), and key idempotency on inChannelId+inHtlcId with a conditional insert. Recover from authoritative records, not from a separately maintained index.

## Constraints (do not violate)

- Do not require a storage adapter feature the published adapters do not have.
- Keep list() working for adapters that already hold data.

## Acceptance criteria

- [ ] Concurrent record() calls for the same hashlock produce exactly one entry and one outgoing HTLC.
- [ ] A crash between the two writes cannot lose the link.
