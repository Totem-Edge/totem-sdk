# OMN-100 — Unilateral update coin verification does not bind sequence, commitment, amount or lineage

**Kind:** sdk-defect  
**Severity:** high  
**Status:** open  
**Packages:** `@totemsdk/omnia`
**Observed versions:** @totemsdk/omnia@4.0.0
**Origin:** Omnia adversarial audit — 26 November 2026 @ `c818f5e` (verified in source)

> reporter id OMN-098
**Source:** `Omnia adversarial audit — 26 November 2026, reporter finding OMN-098 (omnia/src/settlement.ts:490-532)`

## Context

recordUnilateralUpdateCoin verifies the coin exists, is unspent, sits at the expected address and reaches a confirmation depth, then uses its creation height for the contest deadline. It does not check the coin's sequence, state commitment, amount/token or the transaction that produced it.

## Impact

A coin that merely looks right can set the contest deadline, so a dispute can be timed against an unrelated coin. Same class as the splice successor finding; it needs one shared lineage verifier.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia test
```

**Expected:** The update coin is bound to the expected sequence, commitment, amount, token and creating transaction.

**Actual:** Only spent/address/depth are checked.

**Evidence:**

- settlement.ts:505 (spent check)
- no sequence/commitment comparison in the function

## Where to fix


### Approach

Use the shared channel-lineage verifier (transaction body + predecessor consumption + successor state) before accepting the contest deadline.

## Constraints (do not violate)

- Do not duplicate lineage logic per package.
- Fail closed when the chain cannot return the transaction.

## Acceptance criteria

- [ ] A coin with the wrong sequence or commitment is rejected.
- [ ] The deadline derives only from a verified successor.
