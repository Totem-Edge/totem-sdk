# OMN-095 — A factory participant's latest off-chain allocation is not unilaterally enforceable

**Kind:** sdk-gap  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-factory`
**Observed versions:** @totemsdk/omnia-factory@0.8.0
**Origin:** Omnia SDK audit — 25 November 2026 @ `9f882c8` (verified in source)
**Source:** `Omnia SDK audit — 25 November 2026, reporter finding OMN-093`

## Context

The OMN-058 work added an output-enforced distribution branch that reads every share from PREVSTATE and pins destinations, amounts, output count and conservation. But checkpoint enforcement is still optional at the script-builder level, and the distribution implementation states that it covers the latest confirmed allocation only. A newer off-chain allocation therefore has no enforceable on-chain artifact.

## Impact

A participant's economic entitlement can differ from what they can unilaterally take on chain. This is a capability boundary rather than a regression: there are two distinct production modes and only one of them is enforceable. Treating OMN-058 as fully closed overstates the guarantee.

## Reproduce

```bash
cd artifacts/canary && pnpm run canary run 16-omnia-factory
```

**Expected:** The enforceable on-chain entitlement always equals the participant's latest valid allocation, including an off-chain update that no one has checkpointed.

**Actual:** With enforceCheckpoints off, an off-chain allocation change is not represented on chain. With it on, VC open/close and reallocate are refused until the change is checkpointed.

**Evidence:**

- packages/omnia-factory/src/script.ts:329-330 — enforceCheckpoints is optional, off by default
- packages/omnia-factory/src/script.ts:404 — enforceCheckpoints = options.enforceCheckpoints === true
- packages/omnia-factory/src/distribution.ts:1-12 — scope is the latest confirmed allocation

## Where to fix

- `packages/omnia-factory/src/script.ts`
- `packages/omnia-factory/src/distribution.ts`

### Approach

Keep this as a documented release restriction with two named modes: 'confirmed checkpoint factory' (latest confirmed allocation, enforceable) and 'fully off-chain contestable factory' (latest valid off-chain allocation, outstanding). Do not advertise the second until the contest protocol lands.

## Constraints (do not violate)

- Do not describe the factory as fully off-chain-enforceable in docs or manifests.
- Do not close OMN-058 on the strength of the checkpoint branch alone.
- Refuse off-chain allocation changes on a non-checkpointed factory rather than allowing an unenforceable state.

## Acceptance criteria

- [ ] The capability claim distinguishes the two factory modes.
- [ ] A non-checkpointed factory cannot accumulate an unenforceable allocation delta.
- [ ] The limitation is recorded in the RFC and the register rather than only in a code comment.
