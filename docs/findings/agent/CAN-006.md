# CAN-006 — A channel is stored as active and submit reports success before the counterparty has acknowledged

**Kind:** sdk-defect  
**Severity:** critical  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-host`
**Observed versions:** @totemsdk/omnia-host@0.13.4
**Source:** `live runs: omnia-open-noncustodial.mjs against Hawk v0.2.12 and v0.3.0`

## Context

submitOpenChannel writes the channel into the local store as active, then asks the peer. When the peer rejects, the store is not rolled back and the response is still { success: true, acknowledged: false }. The local node therefore reports a live channel that the counterparty has no record of.

## Impact

Funds are committed to a 2-of-2 output whose other party will not co-sign, so the value is unusable until the counterparty is made aware. Any router or UI that reads channel state sees an active channel and will attempt payments that cannot settle. acknowledged=false is easy to ignore and is not reflected in status.

## Reproduce

```bash
pnpm run canary run 44-omnia-noncustodial-live
```

**Expected:** Either the channel is not persisted as active until the ACK arrives, or the failure is recorded on the channel (for example status "pending-ack") and the RPC reports failure.

**Actual:** totem_omniaGetChannelState on the initiator returns status "active" with totalValue 100000000 for channel 0x8e3aac4a4d94b3b45ae5dc4f7317e7ea, while the responder returns "Channel ... not found"; submit returned success:true, acknowledged:false.

**Evidence:**

- initiator A: totem_omniaGetChannelState -> status "active", channelId 0x8e3aac4a4d94b3b45ae5dc4f7317e7ea
- responder B: totem_omniaGetChannelState -> error "Channel 0x8e3aac4a4d94b3b45ae5dc4f7317e7ea not found"
- submit response: {"success":true,"acknowledged":false,"fundingTxId":"0x000101961A785E7B2724D42ADAB585B2CF66487E96A3E6950396E881DA16BD57"}
- the funding output is on chain and unspent, held by MULTISIG(2, A, B)
- 0.3.0: initiator reported status "active" for channel 0xe6863650602f6f7a3e1b99df1ebba8d1 while the responder returned "not found"
- packages/omnia-host/src/api/methods.ts: channels.set(...) happens before requestPeerReply, with no rollback on non-ACK

## Where to fix

- `packages/omnia-host/src/api/methods.ts`
- `packages/omnia/src/store`

### Approach

Make the persisted status reflect what was agreed. Keep the on-chain funding fact, but mark the channel pending acknowledgment until the peer ACKs, and return a non-success result (or an explicit partial result) when the peer rejects. If the channel is left in pending-ack, give it a documented recovery path that re-sends the proposal once the funding coin is visible.

## Constraints (do not violate)

- Do not hide the on-chain funding output; its existence is still true and needed for recovery.
- Do not make the ACK authoritative for the on-chain state (the tx is already posted).
- Do not change the funding script or state contract.

## Acceptance criteria

- [ ] A rejected open is not reported as an active channel by the initiator.
- [ ] The initiator exposes a recoverable pending-ack channel that can be re-proposed and becomes active once the peer ACKs.
- [ ] A normal open still results in status active only after the ACK.
