# OMN-026 — An incoming message can overwrite the cached peer for an unrelated channel

**Kind:** sdk-defect  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-host`
**Observed versions:** @totemsdk/omnia@3.0.0, @totemsdk/omnia-host@0.14.0, @totemsdk/omnia-factory@0.7.2, @totemsdk/omnia-splice@0.3.4, @totemsdk/omnia-vtxo@0.9.0
**Origin:** Totem Edge Omnia whole-family re-audit, 2026-11-17 @ `c81af31` (verified in source)
**Source:** `Omnia host signing audit, 2026-11-18 (verified against 997b7f40)`

## Context

The host cached channelPeers from any inbound message channelId before binding the peer to the channel counterparty. The cache is now updated only when the authenticated peer key is a registered party of the stored channel and is not the local identity.

## Impact

A connected peer that names a channel id can no longer replace the routing cache and receive signed HTLC updates for that channel.

## Reproduce

```bash
npx jest --config tests/jest/omnia-host.cjs --runInBand tests/unit/omnia-host/src/__tests__/peer-guards.test.ts
```

**Expected:** Only a channel counterparty can be cached for the channel.

**Actual:** Fixed: isChannelPeer checks the peer key against channel.parties and excludes the local key.

**Evidence:**

- packages/omnia-host/src/lifecycle.ts onPeerMessage
- packages/omnia-host/src/peer-guards.ts isChannelPeer

## Where to fix

- `packages/omnia-host/src/lifecycle.ts`
- `packages/omnia-host/src/peer-guards.ts`

### Approach

Derive the association from authenticated participant identity and verify it against the channel record before caching.

## Constraints (do not violate)

- Never update the cache merely because a message names a channel.
- Exclude the local identity.

## Acceptance criteria

- [ ] A foreign peer naming a channel cannot become its cached peer.
- [ ] The real counterparty is still cached.

## Tests that prove it
