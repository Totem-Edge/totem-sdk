# OMN-012 — createMultiHopForwarder is exported but never instantiated by the host

**Kind:** sdk-gap  
**Severity:** medium  
**Status:** open  
**Packages:** `@totemsdk/omnia-relay`, `@totemsdk/omnia-host`
**Observed versions:** @totemsdk/omnia-relay@0.7.1, @totemsdk/omnia-host@0.13.4
**Origin:** Totem Edge Omnia whole-family re-audit, 2026-11-17 @ `c81af31` (verified in source)
**Source:** `Omnia whole-family re-audit (2026-11-17), finding OMN-012`

## Context

The forwarding engine exists in omnia-relay and is exported, but no production host path constructs it. Multi-hop forwarding therefore depends on wiring that the reviewed host does not demonstrate.

## Impact

The relay package appears supported while the deployed host cannot forward; a two-hop payment has no executing component.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-relay test
```

**Expected:** A host started with relay enabled constructs the forwarder and drives it from the channel event stream.

**Actual:** Only the export exists; no host call site.

**Evidence:**

- packages/omnia-relay/src/index.ts: export only
- no createMultiHopForwarder call in packages/omnia-host

## Where to fix

- `packages/omnia-host/src/lifecycle.ts`
- `packages/omnia-host/src/api/methods.ts`

### Approach

Either wire the forwarder into the host lifecycle with a durable journal and expose its state, or mark the package explicitly as a library primitive and remove the implied host support from docs and claims.

## Constraints (do not violate)

- Do not advertise multi-hop as available while it is unwired.
- If wired, the journal must be the durable one from OMN-006.

## Acceptance criteria

- [ ] Either the host constructs the forwarder and passes an integration test, or the docs and package maturity state that it is library-only.

## Tests that prove it

- `tests/unit/omnia-host/src/__tests__/relay-wiring.test.ts`
