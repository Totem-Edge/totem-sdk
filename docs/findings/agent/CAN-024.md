# CAN-024 — Omnia writes atom amounts with MiniNumber scale 0, encoding channel values 10^44 times too large

**Kind:** sdk-defect  
**Severity:** critical  
**Status:** fixed  
**Packages:** `@totemsdk/omnia`, `@totemsdk/omnia-host`, `@totemsdk/chain-provider`, `@totemsdk/core`
**Observed versions:** @totemsdk/omnia@3.0.0, @totemsdk/omnia-host@0.14.0, @totemsdk/chain-provider@0.4.0, @totemsdk/core@1.6.0
**Source:** `two-host S4 run (`openChannel` threw `Cannot convert 0.2 to a BigInt`) reviewed against minima-global/Minima `objects/Coin.java`, `objects/base/MiniNumber.java` and `objects/Transaction.java``

## Context

Minima has one amount type, `MiniNumber`: JSON reports it as decimal MINIMA text ("0.2"), while the binary transaction stores `(unscaled, scale)` with value = unscaled x 10^-scale. Omnia kept channel maths in atoms but its canonical serializer wrote atom integers with scale 0, so a 0.2 MINIMA channel was encoded as 2x10^43 MINIMA. Separately, the RPC provider normalised its coin amounts to atoms while Hosted, Lookup and Composite providers stayed decimal, so `ChainStateProvider.getCoins/getCoin` no longer had a single unit contract.

## Impact

Every non-trivial channel funding/update/settlement draft was invalid: `Transaction.checkValid()` requires 0 < amount <= 1,000,000,000 and rejects the encoded value as an invalid Minima amount. The S4 run failed earlier, at `BigInt("0.2")`, which masked the encoding fault. Consumers that expected node decimal text (tx-builder coin selection and serialisation, the extension's `TOTEM_GET_COINS` and selection, edge-adapters and realtime balances) would have been inflated by 10^44 once a provider returned atoms; a composite fallback flipped the unit mid-application.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia test
```

**Expected:** input/output amount is `MiniNumber(unscaled = 2x10^43, scale = 44)`, which Java reads as 0.2 MINIMA and accepts.

**Actual:** the amount was written as `MiniNumber(unscaled = 2x10^43, scale = 0)`, which Java reads as 2x10^43 MINIMA; `isValidMinimaValue()` rejects it.

**Evidence:**

- build a funding draft for 0.2 MINIMA (`totalValue = 2e43` atoms) and decode the serialized coin amount: `buildFundingTx(...)` -> `omniaDraftToCanonicalMinimaBytes(...)`
- minima-global/Minima objects/Coin.java:239 — `amount` JSON is `mAmount.toString()` (decimal text)
- minima-global/Minima objects/base/MiniNumber.java:31-49 — MAX_DECIMAL_PLACES = 44, MINI_UNIT = 1E-44
- minima-global/Minima objects/base/MiniNumber.java:287-299 — binary form is [scale][length][unscaled]
- minima-global/Minima objects/Transaction.java:165 — `isValidMinimaValue()` requires 0 < amount <= 1e9
- packages/omnia/src/transactions.ts: serializeCoinForMinima wrote `writeMiniNumberLocal(opts.amount)` with the default scale 0
- packages/chain-provider/src/providers/minima-rpc.ts: getCoins/getCoin returned atoms while hosted.ts and lookup-client.ts returned decimal

### Approach

Define one contract: providers return node-native decimal text; `@totemsdk/core` owns `amountToAtoms`/`atomsToAmount`/`coinAmountAtoms`; Omnia converts once at its boundary and writes every coin amount as `MiniNumber(unscaled = atoms, scale = 44)`. Value-bearing program state ports use the same scale and the scale is bound into the signed state commitment, so a signer cannot re-encode a port at scale 0. The Rust/WASM mirror uses arbitrary-precision integers and the same scale rules.

## Constraints (do not violate)

- Do not normalise units inside one ChainStateProvider implementation; the interface has one unit.
- Do not write atom amounts with scale 0 anywhere.
- Bind the state-port scale in the commitment; a signed state must not be re-encodable at a different scale.

## Acceptance criteria

- [ ] getCoins/getCoin return decimal text from every provider and a composite fallback cannot change units.
- [ ] A 0.2 MINIMA funding draft decodes to scale 44 with value 0.2 and passes the Java validity bound.
- [ ] Value-bearing state ports round-trip at scale 44; counters/sequences stay scale 0.
- [ ] Rust/WASM digest and commitment parity hold.
