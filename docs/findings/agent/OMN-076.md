# OMN-076 — The splice journal is cleared before the successor channel is persisted

**Kind:** sdk-defect  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-splice`, `@totemsdk/omnia-host`
**Observed versions:** @totemsdk/omnia-splice@0.3.5
**Origin:** Omnia SDK audit — 25 November 2026 @ `9f882c8` (verified in source)
**Source:** `Omnia SDK audit — 25 November 2026, reporter finding OMN-074`

## Context

finalizeSplice() clears the pending record as soon as the successor is observed as active, and only then builds and returns the SplicedChannel object that the caller persists. A crash in that window leaves the predecessor channel in local state, the successor on chain and no recovery record.

## Impact

The failure is unrecoverable without manual chain inspection: the host resumes with a channel whose funding coin is spent, and nothing tells it a splice completed. It is exactly the state the journal exists to prevent.

## Reproduce

```bash
cd artifacts/canary && pnpm run canary run 34-omnia-host-durability
```

**Expected:** Journal completion, predecessor retirement and successor persistence commit together; a crash before commit leaves the splice pending and recoverable.

**Actual:** pendingSpliceStore.clear() runs before splicedChannel is constructed and before the caller can store it.

**Evidence:**

- packages/omnia-splice/src/finalize.ts:381-385 — clear on active
- packages/omnia-splice/src/finalize.ts:387-424 — successor object built afterwards

## Where to fix

- `packages/omnia-splice/src/finalize.ts`
- `packages/omnia-host/src`

### Approach

Reorder so the successor is constructed and durably persisted, the predecessor is marked spliced, and the journal entry is cleared last. Where the host owns the store, pass a completion callback so the journal is cleared only after the channel store commits.

## Constraints (do not violate)

- Never clear the journal before the successor is durable.
- Keep the operation idempotent: a re-run with the journal still present must converge.
- Do not leave the predecessor active after a successful commit.

## Acceptance criteria

- [ ] A crash injected between observation and persistence leaves a recoverable journal entry.
- [ ] A successful finalize persists the successor before clearing the journal.
- [ ] Recovery from either crash window converges on the same splicing state.
