# CAN-005 — The initiator discards the peer ERROR frame, so a rejected open reports only acknowledged=false

**Kind:** sdk-defect  
**Severity:** medium  
**Status:** open  
**Packages:** `@totemsdk/omnia`, `@totemsdk/omnia-host`
**Observed versions:** @totemsdk/omnia@2.4.3, @totemsdk/omnia-host@0.13.4
**Source:** `live runs: omnia-open-noncustodial.mjs against Hawk v0.2.12 and v0.3.0`

## Context

The wire protocol defines an ERROR message carrying payload.error, and the responder sends it with a precise reason. requestPeerReply does receive it, but submitOpenChannel reduces the reply to acknowledged = reply.type === 'ACK' and drops the payload; the integration router has no ERROR branch at all, so the frame is not surfaced anywhere.

## Impact

Every peer-side rejection is opaque to the caller and to the operator log. In this run the actual cause (funding coin not on chain) only became visible after instrumenting the stream layer on the initiator. Support and automation cannot distinguish a rejected proposal from a lost one without patching the SDK.

## Reproduce

```bash
pnpm run canary run 44-omnia-noncustodial-live
```

**Expected:** The submit result or an observation record carries the responder's reason.

**Actual:** Submit returns { success: true, acknowledged: false } with no reason; nothing is logged unless OMNIA_DEBUG is on, and even then only "[omnia-stream] recv ERROR" with no payload.

**Evidence:**

- packages/omnia-host/src/api/methods.ts: acknowledged = reply?.type === 'ACK' (reason not read)
- packages/omnia/src/integration.ts: _sendError sends payload { error: reason } from 10 call sites
- packages/omnia/src/integration.ts: the inbound router switches on CHANNEL_PROPOSAL/STATE_UPDATE/... but has no ERROR case
- packages/omnia/src/stream.ts: debug logging prints the message type only
- temporary logging-only instrumentation showed: {"error":"acceptChannel failed: Error: Funding coin 0x68778de3... not found on chain"}

## Where to fix

- `packages/omnia-host/src/api/methods.ts`
- `packages/omnia/src/integration.ts`

### Approach

Preserve the reason end to end: return it on the submit result (for example acknowledged:false with peerError), include it in the operation record and the observation stream, and handle ERROR explicitly in the integration router so first-contact and routed messages both surface the payload.

## Constraints (do not violate)

- Do not change the ERROR wire format or the reply-matching rules (channelId + nonce).
- Do not turn a rejection into a thrown exception where callers already branch on acknowledged.
- Do not log secrets from the payload; the reason is a short string.

## Acceptance criteria

- [ ] A rejected proposal yields the responder reason to the caller and in the observation record.
- [ ] The canary can assert on the reason without instrumenting node_modules.
