# CAN-023 — Hawk 0.3.0 cannot complete mainnet IBD: block proofs rejected, blocks skipped, tip parks ~1,000 behind

**Kind:** environment-blocked  
**Severity:** high  
**Status:** in-progress  
**Packages:** `hawk-node`
**Source:** `live run 15 Nov 2026: mainnet node on host A (us-east-1), 0.3.0 vs 0.2.12`

## Context

A fresh Hawk 0.3.0 node on mainnet (no -test, no -solo) syncs to block 2,418,985 and then loops on "Invalid MMR Proof! @ 2418985", never advancing and never binding the RPC port. The 0.2.12 release, started on the same host minutes later, completed IBD to block 2,421,050 via cascade with zero MMR errors.

## Impact

The canary gate requires Hawk 0.3.0 (exact match), so no live scenario can run against the current build on mainnet. Factory, channel and settlement evidence cannot be produced until 0.3.0 syncs or the gate is given a documented exception.

## Reproduce

```bash
pnpm run canary run 44-omnia-noncustodial-live
```

**Expected:** The node reaches /readyz 200 on mainnet and the run proceeds.

**Actual:** readyz stays 000; the log repeats "Invalid MMR Proof! @ 2418985" for the same block indefinitely.

**Evidence:**

- root cause 4 (residual 171->998 MMR lines at the tip): checkMMR validated a block's own witness proofs against the parent MMR. Blocks that carry their own coin set (superblocks) can never match it; the block's coin set is bound by its own MMR root, which checkTxPoWBlock/blockStateMatches rebuild and compare. Skipping the per-proof check for blocks (transactions stay strict) gives 0 MMR lines in 150s while the chain advanced 6 blocks, versus ~3/min before
- root cause 3 found: checkTxBlockOnly compares the block difficulty against a trailing average over the local tree, which cannot match for a historical IBD block. Block 2420149 failed with "Incorrect TxPoW block difficulty" and everything after was skipped for a missing parent
- with all three fixes the same build synced from scratch on mainnet to block 2421363 against a peer top of 2421362, syncing 0, zero difficulty rejections (171 residual MMR lines, non-blocking)
- experiments rejected: reverting tx_pow_tree to 0.2.12 (sort order + side-branch collection) still parks at 2420225 and raises MMR errors to 754; setSyncIBD call sites are identical in both versions
- residual is in IBD peer/response selection: the node loops asking a peer whose batch top (2420114) is below its own tip (2420148) and discards the blocks as historical; IBD_LIMIT_MINS is new in 0.3.0
- root cause 2 found: the one-greeting-per-connection guard (new in 0.3.0) returns early on the duplicate, suppressing the IBD retry that 0.2.12 used to obtain its cascade. With the guard relaxed a fresh node logged Cascade: Loading 3361 nodes within a minute and reached the cascade tip with 0 MMR errors
- both fixes are on minima-more PR #2; residual: after adopting the cascade the node sits at the cascade tip and loops requesting IBD at tip-1, receiving batches that end below its tip and are ignored as historical
- after threading the offset through checkTxPoWSimple for transactions inside a block: still parks, this time at 2420143 with 411 MMR errors, readyz 200, syncing 0, ~1090 blocks behind the peer
- hundreds of "SyncBlock missing parent (skipping, not fatal)" lines: the tree is rebuilt from a subset, so the batch top is never reached and the IBD loop finishes early
- with the block-proof offset fix (minima-more PR #2): 0 Invalid MMR Proof, RPC binds, but the node then stalls at "No TxPoWTree yet.. required for NIO_SYNCTXBLOCK" and never receives a cascade; readyz stays 503 after 13 minutes
- 0.2.12 on the same host logs "Cascade: Loading 3361 nodes" and reaches block 2421050
- 0.3.0: peer ahead top=2421118, IBD requested, tip stuck at 2418985, RPC never bound
- 0.3.0 log: 200+ lines of "Invalid MMR Proof! @ 2418985", tip unchanged for >3 minutes
- 0.2.12 on the same host: readyz 200, block 2421050, syncing 0, 0 MMR errors, ~2 min via cascade
- witnessesMatch (blockStateMatches) verifies coin proofs with parentMMR.checkProof because block proofs are one block ahead, but the sync path calls checkTxBlockOnly/checkTxPoWSimple first, which use checkProofTimeValid against the parent MMR

## Where to fix

- `hawk-node: org/minima/system/brains/tx_po_w_checker.cpp`
- `hawk-node: org/minima/system/brains/tx_po_w_processor.cpp`

### Approach

Make the sync-block path use the same one-block-ahead proof semantics that blockStateMatches already uses, for the block TxPoW and any local transaction bodies, instead of checkProofTimeValid against the parent MMR. Then re-run mainnet IBD on a clean data dir and require the tip to track the peer.

## Constraints (do not violate)

- Do not disable the witness gate by default to hide this: IBD_WITNESS_CHECK is already false.
- Do not weaken blockStateMatches while fixing the earlier check.

## Acceptance criteria

- [ ] A fresh 0.3.x node on mainnet reaches readyz 200 and tracks the peer tip across a cascade boundary.
- [ ] No "Invalid MMR Proof" loop at any height.
