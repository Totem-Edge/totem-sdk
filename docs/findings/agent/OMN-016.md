# OMN-016 — Channel locking is keyed by the RPC channelId and multi-channel paths escape it

**Kind:** sdk-gap  
**Severity:** medium  
**Status:** open  
**Packages:** `@totemsdk/omnia-host`
**Tracked as:** `CAN-022` — this id is the audit's alias; the canonical entry owns the fix.
**Observed versions:** @totemsdk/omnia-host@0.13.4
**Origin:** Totem Edge Omnia whole-family re-audit, 2026-11-17 @ `c81af31` (verified in source)
**Depends on:** `OMN-001` — land those first.
**Source:** `Omnia whole-family re-audit (2026-11-17), finding OMN-016`

## Context

withChannelLock is applied where a channelId is present, but prepared-operation and multi-channel paths can touch several channels without entering a common critical section. Locking on a caller-supplied id also lets a caller serialize against the wrong key.

## Impact

Concurrent operations on the same channel can interleave through a path that did not take the lock.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-host test
```

**Expected:** Any handler that mutates channel state holds a lock keyed by the channel it derives, not the request.

**Actual:** Some paths take no lock or use the request channelId.

**Evidence:**

- packages/omnia-host/src/api/methods.ts: withChannelLock call sites
- packages/omnia-host/src/channel-lock.ts

## Where to fix

- `packages/omnia-host/src/api/methods.ts`
- `packages/omnia-host/src/channel-lock.ts`

### Approach

Derive lock keys from the resolved channel(s), take them in a stable order for multi-channel operations, and cover prepared-operation commits.

## Constraints (do not violate)

- No deadlock: multi-channel locks must be ordered.
- Re-entrancy must keep working.

## Acceptance criteria

- [ ] A concurrent test over the same channel cannot interleave.
- [ ] A multi-channel operation takes both locks in a deterministic order.

## Tests that prove it
