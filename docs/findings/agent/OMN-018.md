# OMN-018 — Auto-approval has no mandatory bound (hardening, not a defect)

**Kind:** sdk-gap  
**Severity:** low  
**Status:** open  
**Packages:** `@totemsdk/omnia-host`
**Observed versions:** @totemsdk/omnia-host@0.13.4
**Origin:** Totem Edge Omnia whole-family re-audit, 2026-11-17 @ `c81af31` (disputed — see note)

> Downgraded from P2: the gate is deny-by-default and both bounds exist and are enforced. The residual issue is that an operator may opt into auto-approval without a bound; that is configuration hardening, not the unbounded-automation defect the report describes.
**Source:** `Omnia whole-family re-audit (2026-11-17), finding OMN-018`

## Context

The gate is deny-by-default and supports both `maxTotalValue` and `allowedPeers`, and both are enforced. `autoApprove: true` with neither bound is still permitted, so an operator can opt into unbounded signing.

## Impact

A misconfigured unattended host can sign any factory a peer asks for. The default configuration is safe.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-host test
```

**Expected:** Enabling auto-approval without a bound is rejected at construction.

**Actual:** It is accepted; every request is then allowed.

**Evidence:**

- packages/omnia-host/src/factory-approval.ts: allowedPeers and maxTotalValue are optional

## Where to fix

- `packages/omnia-host/src/factory-approval.ts`

### Approach

Require at least one bound when `autoApprove` is set, and log the effective policy at startup. Keep the existing defaults and the authorizer hook unchanged.

## Constraints (do not violate)

- Do not change the default-deny behaviour.
- Do not make an explicit operator authorizer require the bounds.

## Acceptance criteria

- [ ] `autoApprove` without `maxTotalValue` or `allowedPeers` throws at construction.
- [ ] A bounded policy still auto-approves within its bounds.

## Tests that prove it
