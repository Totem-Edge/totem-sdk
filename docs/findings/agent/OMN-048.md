# OMN-048 — Duplicate incoming state updates could consume multiple WOTS key pairs at the same sequence

**Kind:** sdk-defect  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia`, `@totemsdk/omnia-host`
**Observed versions:** @totemsdk/omnia@3.0.0, @totemsdk/omnia-host@0.14.0, @totemsdk/omnia-factory@0.7.2, @totemsdk/omnia-vtxo@0.9.0, @totemsdk/omnia-pool@0.6.0, @totemsdk/liquidity-bond@0.4.0, @totemsdk/omnia-router@0.4.2, @totemsdk/omnia-splice@0.3.4, @totemsdk/chain-provider@0.4.0, @totemsdk/core@1.6.0
**Origin:** Totem Edge Omnia whole-family re-audit, 2026-11-17 @ `c81af31` (verified in source)
**Source:** `Deeper Omnia covenant/transaction audit, 2026-11-18 (verified against 51aed956)`

## Context

STATE_UPDATE handling was not serialized per channel, so identical retries each reserved and committed two WOTS leaves. Inbound updates are now serialized per channel and identical (channel, sequence, commitment) retries reuse the recorded ACK instead of signing again.

## Impact

Signing capacity could be consumed without advancing the channel, and one logical update could yield several ACK signatures.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia test
```

**Expected:** An identical retry reuses the recorded reply.

**Actual:** Fixed: per-channel serialization plus a reply cache.

**Evidence:**

- packages/omnia/src/integration.ts _handleStateUpdate
- packages/omnia/src/sign.ts signState

## Where to fix

- `packages/omnia/src/integration.ts`

### Approach

Serialize per channel and key replies by sequence+commitment.

## Constraints (do not violate)

- Never reserve a second pair of leaves for one commitment.

## Acceptance criteria

- [ ] Identical retries produce one signature.
- [ ] Both retries receive an ACK.
