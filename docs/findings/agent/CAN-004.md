# CAN-004 — Non-custodial channel open races the chain: the acceptor validates the funding coin before it can be mined

**Kind:** sdk-defect  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia`, `@totemsdk/omnia-host`
**Observed versions:** @totemsdk/omnia@2.4.3, @totemsdk/omnia-host@0.13.4
**Source:** `live runs: omnia-open-noncustodial.mjs against Hawk v0.2.12 and v0.3.0 (us-east-1 hosts A/B)`

## Context

SubmitOpenChannel posts the funding transaction and, in the same call, sends CHANNEL_PROPOSAL to the counterparty. The responder's acceptChannel requires the funding coin to already exist on chain and throws "Funding coin <id> not found on chain". On a real node the transaction cannot be included in a block in the microseconds between the post and the proposal, so a first-time open always fails. The initiator does not wait for inclusion, and the responder does not wait or retry.

## Impact

Every two-party channel open against a live node fails at the peer handshake, even though the funding transaction is valid and is mined moments later. Offline and in-memory suites do not catch it because their chain view already contains the coin when the proposal is handled. This blocks every channel-based use case from being opened on a real network.

## Reproduce

```bash
pnpm run canary run 44-omnia-noncustodial-live
```

**Expected:** The responder accepts the proposal and reports status "active" for the channel.

**Actual:** Submit returns success with acknowledged=false; the responder answers CHANNEL_PROPOSAL with ERROR "acceptChannel failed: Error: Funding coin <id> not found on chain"; the status poll on the responder never finds the channel.

## Where to fix

- `packages/omnia-host/src/api/methods.ts`
- `packages/omnia/src/channel.ts`

### Approach

Make the handshake tolerate the inclusion delay instead of assuming it away. On the initiator, wait for the funding coin to be observable through the chain provider (bounded, with a named timeout) before sending CHANNEL_PROPOSAL; on the responder, treat "coin not yet found" as retryable for a bounded window rather than an immediate terminal rejection. Either side alone fixes the common case; doing both covers a slow block and a fast initiator.

## Constraints (do not violate)

- Do not remove the on-chain funding-coin check: it is what stops an unfunded channel from being accepted.
- Do not raise the existing 20s peer-reply timeout as the mechanism; the wait belongs around chain inclusion.
- Do not add an unbounded wait or a sleep-and-hope; bound it and fail with the observed height and coin id.

## Acceptance criteria

- [ ] A open against a live node succeeds when the funding tx is mined a few seconds after submission.
- [ ] An open whose funding tx is never mined fails within a bounded time with a message naming the coin and the chain height.
- [ ] The responder still rejects a proposal whose funding coin does not exist (no regression in the safety check).
- [ ] Offline and in-memory suites still pass.
