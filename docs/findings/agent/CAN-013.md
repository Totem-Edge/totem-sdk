# CAN-013 — withChannelLock only guards the direct pay path

**Kind:** sdk-defect  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-host`
**Observed versions:** @totemsdk/omnia-host@0.13.4
**Source:** `security audit OMN-NEW-007, verified against source at 8fa26907`

## Context

withChannelLock is defined once and used exactly once, around the direct omniaPay RPC. HTLC operations, prepared submissions, settlement and splice paths do not take it, so they can read, modify and write the same channel concurrently.

## Impact

Concurrent RPC or peer-driven operations can interleave read-modify-write cycles. The signing watermark blocks some conflicting signatures but does not serialize state derivation, so a lost update or a state built on a stale sequence is possible.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-host test
```

**Expected:** Every channel mutation, whatever its entry point, runs under one per-channel coordinator.

**Actual:** One use of withChannelLock, in the direct pay handler.

**Evidence:**

- fix proposed in PR #218 (shared re-entrant per-channel lock across RPC and peer handlers)
- packages/omnia-host/src/api/methods.ts:2025 — const withChannelLock = ...
- packages/omnia-host/src/api/methods.ts:2408 — the only call site

## Where to fix

- `packages/omnia-host/src/api/methods.ts`
- `packages/omnia-host/src/lifecycle.ts`

### Approach

Move the lock into the channel store or a mutation coordinator and take it in every path that mutates a channel: pay, HTLC add/reveal/timeout, prepared submit, settlement and splice, including peer handlers.

## Constraints (do not violate)

- Do not rely on the watermark as the serialization mechanism.
- Do not introduce a global lock that serializes unrelated channels.

## Acceptance criteria

- [ ] All mutation entry points acquire the same per-channel lock.
- [ ] A concurrency test that interleaves two mutations yields a consistent sequence with no lost update.
