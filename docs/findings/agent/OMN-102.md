# OMN-102 — The distributed multi-hop branch bypasses the durable operation lifecycle

**Kind:** sdk-defect  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-host`, `@totemsdk/omnia-router`
**Observed versions:** @totemsdk/omnia-host@0.16.0, @totemsdk/omnia-router@0.6.0
**Origin:** Omnia adversarial audit — 26 November 2026 @ `c818f5e` (verified in source)

> reporter id OMN-100
**Source:** `Omnia adversarial audit — 26 November 2026, reporter finding OMN-100 (omnia-host/src/api/methods.ts:4085-4146)`

## Context

The distributed payment branch creates an HTLC, persists the channel and sends the message, returning before the withOperation wrapper used by the local branch. It reports first-hop-accepted after sending without an explicit acknowledgement.

## Impact

Distributed payments lack the operation journal, idempotency and unknown-outcome handling added for local execution, and can report acceptance the peer never gave.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-host test
```

**Expected:** Every payment path uses the same durable execution lifecycle.

**Actual:** The distributed branch returns outside withOperation.

**Evidence:**

- methods.ts:4085-4146 (early return before withOperation)
- withOperation at methods.ts:506

## Where to fix


### Approach

Route the distributed branch through withOperation with an operation id, persist the signed proposal, wait for acknowledgement and record refund obligations.

## Constraints (do not violate)

- Do not require a local channel for the distributed path.
- Reuse the relay delivery journal for retransmission.

## Acceptance criteria

- [ ] A retried distributed payment is idempotent.
- [ ] Acceptance is reported only after acknowledgement.
- [ ] Undelivered proposals are recoverable.
