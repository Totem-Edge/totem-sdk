# OMN-074 — A splice successor is identified by address, token and amount only, not by lineage from the splice

**Kind:** sdk-defect  
**Severity:** critical  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-splice`
**Tracked as:** `CAN-012` — this id is the audit's alias; the canonical entry owns the fix.
**Observed versions:** @totemsdk/omnia-splice@0.3.5
**Origin:** Omnia SDK audit — 25 November 2026 @ `9f882c8` (verified in source)
**Source:** `Omnia SDK audit — 25 November 2026, reporter finding OMN-072`

## Context

observeSpliceSuccessor() selects the successor coin by matching address, token id and amount among unspent coins, and excludes spent coins. It does not establish that the coin was created by the intended splice transaction, and it does not explicitly exclude the predecessor funding coin. Rejecting two or more matches does not cover the single-wrong-match case.

## Impact

A channel can be activated against a coin the splice did not create, or against an incorrect state commitment. The guard against ambiguity is real but narrow: any single unrelated coin with the same address, token and amount is adopted silently.

## Reproduce

```bash
cd artifacts/canary && pnpm run canary run 18-omnia-splice
```

**Expected:** The successor is accepted only when the splice transaction is on chain, consumed the predecessor, and created this coin with the expected state, sequence and balance commitment.

**Actual:** Observation is a set filter over getCoins(address, tokenId). A coin funded to the same channel address by an unrelated transaction satisfies it.

**Evidence:**

- packages/omnia-splice/src/successor.ts:74-118 — candidates filter on spent/address/tokenid/amount
- packages/omnia-splice/src/successor.ts:88-96 — multi-match rejection only
- CAN-012 records the ambiguity case; the lineage case is still open

## Where to fix

- `packages/omnia-splice/src/successor.ts`
- `packages/omnia-splice/src/finalize.ts`

### Approach

Verify transaction lineage before activation: the splice tx must be mined, its first input must be the predecessor coin, and the successor must appear among its outputs with the expected state variables, sequence and total. Then observe burial depth on that coin id.

## Constraints (do not violate)

- Do not rely on a predicted coin id: the channel input floats (COINID_ELTOO).
- Do not weaken the multi-match rejection; add lineage on top.
- Fail closed when the chain adapter cannot return the spending transaction.

## Acceptance criteria

- [ ] A coin with a matching address/token/amount but a different creating transaction is rejected.
- [ ] The predecessor coin is never accepted as its own successor.
- [ ] Successor sequence and balance commitment are checked against the accepted splice terms.
