# OMN-003 — A transferred VTXO keeps the previous owner's exit entitlement

**Kind:** sdk-defect  
**Severity:** critical  
**Status:** open  
**Packages:** `@totemsdk/omnia-vtxo`
**Observed versions:** @totemsdk/omnia-vtxo@0.8.1
**Origin:** Totem Edge Omnia whole-family re-audit, 2026-11-17 @ `c81af31` (verified in source)
**Source:** `Omnia whole-family re-audit (2026-11-17), finding OMN-003`

## Context

transferVtxo verifies `params.exitEntitlement` against the input VTXO, then copies the same object onto the output VTXO, whose owner and vtxoId are both new. verifyVtxoExitEntitlement binds owner, vtxoId, amount and holderIndex, so the attached artifact cannot verify for the recipient — and the exit transaction pays the previous owner. The entitlement is also optional, so a transfer may attach none at all.

## Impact

A recipient receives a VTXO with an exit that pays the sender, or no exit. Any consumer that treats the presence of `exitEntitlement` as proof of a recipient-executable exit can lose the value.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-vtxo test
```

**Expected:** verifyVtxoExitEntitlement(outputVtxo, outputVtxo.exitEntitlement).valid === true after a transfer.

**Actual:** The entitlement still names the input owner/vtxoId, so verification against the output fails on vtxoId, owner and holderIndex.

**Evidence:**

- packages/omnia-vtxo/src/transfer.ts: verify against `vtxo`, then spread `params.exitEntitlement` onto `outputVtxo`
- packages/omnia-vtxo/src/exit-entitlement.ts: verify checks vtxoId, owner, amount, holderIndex
- packages/omnia-vtxo/src/exit-tx.ts: output 0 pays `wotsAddressData(params.vtxo.owner)`

## Where to fix

- `packages/omnia-vtxo/src/transfer.ts`
- `packages/omnia-vtxo/src/exit-entitlement.ts`

### Approach

Build the recipient's exit from the output VTXO (recipient as holderIndex owner, output id, same amount) and verify it before returning. Either require an exit for a full transfer or make the absence explicit in the result so callers cannot mistake it for an executable claim.

## Constraints (do not violate)

- Do not mutate the input entitlement into the output; rebuild it.
- Partial transfers must not inherit an entitlement.
- The exit transaction must still spend the same pool coin and preserve the remainder output.

## Acceptance criteria

- [ ] A two-owner transfer produces an entitlement that verifies against the output.
- [ ] A transfer without an entitlement reports that explicitly and is never described as exit-ready.
- [ ] A partial transfer cannot carry an exit entitlement.
