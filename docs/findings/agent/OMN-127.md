# OMN-127 — Virtual-channel planning accepts the same participant twice

**Kind:** sdk-defect  
**Severity:** high  
**Status:** open  
**Packages:** `@totemsdk/omnia-factory`
**Observed versions:** @totemsdk/omnia-factory@0.9.0
**Origin:** Omnia adversarial audit — 26 November 2026 @ `c818f5e` (verified in source)

> reporter id OMN-125
**Source:** `Omnia adversarial audit — 26 November 2026, reporter finding OMN-125 (omnia-factory/src/virtual.ts:114-168)`

## Context

buildVirtualChannelOpen checks that both supplied participants exist but not that they differ. Identical ids make both allocation deductions target one key, so one assignment overwrites the other.

## Impact

A malformed plan can produce a commitment with a self-referential allocation.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-factory test
```

**Expected:** The planner rejects duplicate participants before producing a commitment.

**Actual:** Distinctness is not checked.

**Evidence:**

- virtual.ts:114-168

## Where to fix


### Approach

Reject identical party ids before any allocation mutation or signing.

## Constraints (do not violate)

- Keep the downstream script guard as defence in depth.
- Do not produce a commitment on a rejected plan.

## Acceptance criteria

- [ ] Identical participants are rejected.
- [ ] A valid pair still plans.
