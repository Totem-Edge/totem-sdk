# CAN-012 — Splice successor selection matches on address, token and amount only

**Kind:** sdk-defect  
**Severity:** medium  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-splice`
**Observed versions:** @totemsdk/omnia-splice@0.3.2
**Source:** `security audit OMN-NEW-006, verified against source at 8fa26907`

## Context

observeSpliceSuccessor picks the first unspent coin whose address, token and amount match. Nothing binds the candidate to the splice transaction that created it or to the expected state transition, and the first match wins rather than treating ambiguity as an error.

## Impact

Two same-value coins at the same script address (a common shape for channel funding addresses) can make the host adopt the wrong coin as the spliced channel. Downstream operations then reference a coin the channel does not control.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-splice test
```

**Expected:** The successor is identified by provenance (txid/output index) or ambiguity is rejected.

**Actual:** coins.find(...) on address+token+amount returns the first candidate.

**Evidence:**

- fix proposed in PR #218 (ambiguous successor is an error)
- packages/omnia-splice/src/successor.ts:83 — const candidate = coins.find((coin) => !coin.spent && address && tokenid && amount)

## Where to fix

- `packages/omnia-splice/src/successor.ts`

### Approach

Accept an expected txid/output reference derived from the splice transaction, or read the successor from the spends of the predecessor coin. If more than one candidate matches, fail as ambiguous instead of choosing.

## Constraints (do not violate)

- Do not silently pick a candidate when several match.
- Keep the bounded polling and confirmation semantics.

## Acceptance criteria

- [ ] Duplicate same-value coins at the address produce an ambiguity error, not a silent pick.
- [ ] The correct successor is still found in the single-candidate case.
