# OMN-116 — Splice acceptance can regress a finalized record

**Kind:** sdk-defect  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-splice`
**Observed versions:** @totemsdk/omnia-splice@0.4.0
**Origin:** Omnia adversarial audit — 26 November 2026 @ `c818f5e` (verified in source)

> reporter id OMN-114; fixed with a monotonic store state machine: saveAcceptance refuses a finalized record and a conflicting second acceptance (an identical replay is idempotent), and markFinalized requires an accepted splice
**Source:** `Omnia adversarial audit — 26 November 2026, reporter finding OMN-114 (omnia-splice/src/durable-splice-store.ts:122-145)`

## Context

saveAcceptance sets the record status to accepted without checking the current status, so a delayed or replayed acceptance can overwrite a record already marked finalized.

## Impact

Recovery can re-enter the finalize path for an already-finalized splice.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-splice test
```

**Expected:** Splice records follow a monotonic state machine and acceptances are immutable once bound.

**Actual:** saveAcceptance writes accepted unconditionally.

**Evidence:**

- durable-splice-store.ts:122-145

## Where to fix


### Approach

Add a monotonic transition table and reject acceptance once finalized.

## Constraints (do not violate)

- Keep pending→accepted→finalized ordering.
- Do not accept a different acceptance for the same splice.

## Acceptance criteria

- [ ] A replayed acceptance cannot regress finalized.
- [ ] A conflicting acceptance is rejected.
