# OMN-073 — Decimal parsing in the LSP truncates precision and mis-signs negative input

**Kind:** sdk-defect  
**Severity:** medium  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-lsp-provider`, `@totemsdk/omnia-lsp`
**Observed versions:** @totemsdk/omnia-lsp-provider@0.1.0
**Origin:** Omnia SDK audit — 25 November 2026 @ `9f882c8` (verified in source)
**Source:** `Omnia SDK audit — 25 November 2026, reporter finding OMN-071`

## Context

decimalKey() splits on '.', multiplies the whole part by 10^18 and adds the fraction padded or sliced to 18 digits. Fractional precision beyond 18 places is silently truncated, a negative value adds a positive fraction to a negative whole (so -1.5 parses as -0.5), and malformed or empty parts reach BigInt() and throw. The same function is duplicated in quote.ts, so the two copies can drift.

## Impact

Amount comparisons and fee arithmetic can be off by a truncation unit, and a negative amount is interpreted as a different number instead of being rejected. Throwing from BigInt surfaces as an opaque error rather than a policy refusal.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-lsp-provider test
```

**Expected:** A shared strict parser accepts a canonical non-negative decimal with at most the asset's precision and rejects everything else with a structured error.

**Actual:** decimalKey('-1.5') yields -500000000000000000n; '1.0000000000000000001' truncates to 1; 'abc' throws SyntaxError from BigInt.

**Evidence:**

- packages/omnia-lsp-provider/src/policy.ts:44-50 — decimalKey
- packages/omnia-lsp-provider/src/quote.ts:18-24 — duplicate decimalKey

## Where to fix

- `packages/omnia-lsp-provider/src/policy.ts`
- `packages/omnia-lsp-provider/src/quote.ts`
- `packages/omnia-lsp/src`

### Approach

Replace both copies with one strict parser in @totemsdk/omnia-lsp: /^(0|[1-9][0-9]*)(\.[0-9]+)?$/, reject negative values, reject excess precision instead of truncating, and return a discriminated result rather than throwing.

## Constraints (do not violate)

- One implementation, shared by policy, quote and any future fee code.
- Do not silently round: excess precision is a rejection.
- Keep the on-wire decimal string format unchanged.

## Acceptance criteria

- [ ] Negative, malformed and over-precise amounts are refused with a policy error.
- [ ] policy.ts and quote.ts no longer contain their own parsers.
- [ ] Valid amounts round-trip through parse and format unchanged.
