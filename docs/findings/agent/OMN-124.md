# OMN-124 — Confirmation depth is computed differently across packages

**Kind:** sdk-defect  
**Severity:** high  
**Status:** open  
**Packages:** `@totemsdk/chain-provider`, `@totemsdk/omnia`
**Observed versions:** @totemsdk/chain-provider@0.5.0, @totemsdk/omnia@4.0.0
**Origin:** Omnia adversarial audit — 26 November 2026 @ `c818f5e` (verified in source)

> reporter id OMN-122
**Source:** `Omnia adversarial audit — 26 November 2026, reporter finding OMN-122 (chain-provider/src/verify-deposit.ts:52-85, omnia/src/chain-truth.ts:29-37)`

## Context

Omnia computes depth as tip minus creation height; the deposit verifier computes tip minus creation height plus one, and also treats a positive MMR entry as confirmation. Two packages can disagree about the same coin reaching a threshold.

## Impact

The same coin can be confirmed for one purpose and unconfirmed for another, so activation and deposit gates disagree.

## Reproduce

```bash
pnpm --filter @totemsdk/chain-provider test
```

**Expected:** One shared confirmation definition.

**Actual:** Two definitions with a one-block offset.

**Evidence:**

- verify-deposit.ts:52-85
- chain-truth.ts:29-37

## Where to fix


### Approach

Export one confirmation helper from chain-provider and use it everywhere.

## Constraints (do not violate)

- Keep the conservative definition.
- Do not change activation semantics silently.

- [ ] Boundary tests cover tip == created and tip == created + n.
