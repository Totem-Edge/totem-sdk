# OMN-090 — Pool payout trusts caller-supplied position and intent instead of the registry

**Kind:** sdk-defect  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-pool`
**Observed versions:** @totemsdk/omnia-pool@0.6.2
**Origin:** Omnia SDK audit — 25 November 2026 @ `9f882c8` (verified in source)
**Source:** `Omnia SDK audit — 25 November 2026, reporter finding OMN-088`

## Context

executePoolPayout() checks params.intent.status === 'approved' and verifies settlement evidence, then derives the accounting transition from params.position and params.intent directly. It never resolves the authoritative position or withdrawal intent from the registry it is given, and never compares them.

## Impact

A stale or inconsistent position object can drive a new accounting transition: the payout can be computed against an amount, status or receipt that the registry has already superseded. Directly relevant to Pool 001, where LP capital accounting is the thing being protected.

## Reproduce

```bash
cd artifacts/canary && pnpm run canary run 24-omnia-pool-001-rehearsal
```

**Expected:** The payout resolves the position and intent from the registry, requires the caller's inputs to match, and binds the transition to the registry revision it consumed.

**Actual:** A position with an inflated amount is paid out without the registry being consulted.

**Evidence:**

- packages/omnia-pool/src/withdraw.ts:225-247 — executes from params.position/params.intent
- no registry position lookup exists in the payout path

## Where to fix

- `packages/omnia-pool/src/withdraw.ts`

### Approach

Load the position and intent from the registry by id, require them to match the supplied objects (or reject the supplied objects entirely), and carry the registry revision into the accounting update so a concurrent mutation is detected.

## Constraints (do not violate)

- The registry is the only authority for position state.
- A missing registry record is an error, not a reason to use the caller's copy.
- The transition must be revision-bound so it cannot apply twice.

## Acceptance criteria

- [ ] A position that differs from the registry is refused.
- [ ] A payout against a superseded intent is refused.
- [ ] The accounting update records the registry revision consumed.
