# OMN-024 — Payments report success before the counterparty co-signs

**Kind:** sdk-defect  
**Severity:** high  
**Status:** fixed  
**Packages:** `@totemsdk/omnia-host`, `@totemsdk/omnia`
**Observed versions:** @totemsdk/omnia@3.0.0, @totemsdk/omnia-host@0.14.0, @totemsdk/omnia-factory@0.7.2, @totemsdk/omnia-splice@0.3.4, @totemsdk/omnia-vtxo@0.9.0
**Origin:** Totem Edge Omnia whole-family re-audit, 2026-11-17 @ `c81af31` (verified in source)
**Source:** `Omnia host signing audit, 2026-11-18 (verified against 997b7f40)`

## Context

omnia/pay calls updateState (a locally signed partial state), stores it, emits committed, sends STATE_UPDATE and returns success. It never waits for the peer ACK or calls attachCounterpartySignature, even though the integration ACK already carries counterpartyPartialState and the close package.

## Impact

The API can report a payment that only one party signed. Stored balances/sequence can diverge from the last jointly enforceable state, and a rejection/timeout is invisible to the caller.

## Reproduce

```bash
pnpm --filter @totemsdk/omnia-host test
```

**Expected:** success is returned only after the peer co-signature is verified and durably stored.

**Actual:** methods.ts pay returns success immediately after sending the state update.

**Evidence:**

- packages/omnia-host/src/api/methods.ts omnia/pay
- packages/omnia/src/channel.ts updateState (partial state)
- packages/omnia/src/integration.ts ACK payload (partialState, counterpartyClosePackage)

## Where to fix

- `packages/omnia-host/src/api/methods.ts`
- `packages/omnia/src/channel.ts`

### Approach

Add prepared → locally-signed → peer-signed → fully-validated → committed stages. Collect the ACK, merge with attachCounterpartySignature, verify the complete state/close package, persist, then report success.

## Constraints (do not violate)

- Never advertise a payment on a one-party state.
- Do not advance the authoritative balance until both signatures are stored.
- Keep failure/timeout explicit.

## Acceptance criteria

- [ ] A payment succeeds only after the ACK signature is merged and verified.
- [ ] A timeout/rejection returns a non-success result and leaves the prior state authoritative.
- [ ] Retries are idempotent.
