# RFC-073 — Hawk Node Command Mapping and Provider Contract

**Status:** Draft — documents the implemented Hawk-node 1.0.100.0 command surface (132 commands) and the `ChainStateProvider` mapping; the provider-boundary migration remains under RFC-062 Amendment A.
**Priority:** P1
**Created:** 2026-10-26
**Authors:** Totem SDK Contributors
**Depends on:** RFC-062 (Node/Extension Pairing), RFC-062 Amendment A (Axia/Hawk Provider Parity), RFC-013 (Wallet Self-Hosted Mode), RFC-014 (Wallet Connect Parity), node RFC-0011 (Capability Manifest)
**Touches:** `packages/minima-rpc`, `packages/chain-provider`, `extensions/totem-extension`, `scripts/generate-minima-rpc-commands.mjs`, `hawk-node` `COMMAND_REFERENCE.md`

> **Positioning.** The extension can pair with a local Hawk node and read chain
> state, but until now the mapping from SDK/extension operations to node RPC
> commands existed only implicitly in generated metadata and adapter methods.
> This RFC makes that mapping normative: one pinned command surface, one
> parameter contract, one provider-to-command table, and one drift check. It
> documents what is already implemented; it does not change node consensus or
> authorise new node commands.

---

## 1. Summary

This RFC decides:

1. **One source of truth.** The node's capability manifest (node RFC-0011),
   emitted as `hawk-node/COMMAND_REFERENCE.md`, is the only source of command
   names, parameters, required/optional markers and enums.
2. **Generated, never hand-edited.** `packages/minima-rpc/src/commands.generated.ts`
   is generated by `scripts/generate-minima-rpc-commands.mjs` and checked for
   drift. Hand edits are rejected.
3. **Named-parameter wire format.** Commands are sent as
   `command name:value name:value …` over HTTP `POST` with `Content-Type:
   text/plain`; the SDK validates required values, unknown names, enums and
   coarse types before sending.
4. **A typed provider boundary.** `ChainStateProvider` is the extension's
   contract; every method maps to an explicit node command (or a documented
   client composition).
5. **Explicit unknown-command escape hatch.** `runCommand(cmd, params)` is the
   only passthrough. Typed provider methods never use it for unmapped behaviour.
6. **Typed errors.** Failures surface as `MinimaRpcError` carrying the command,
   the node's `error` text and the HTTP status when available.
7. **No whitespace injection.** Parameter values containing whitespace or
   control characters are rejected, never silently escaped, because the wire
   format is space-delimited.
8. **Pinned node surface.** The generated file records the node command-reference
   version it was built from. Command-set changes require regeneration and a
   version bump, not a tolerant fallback.
9. **Documented gaps stay explicit.** Capability routing/mode isolation
   (RFC-062 Amendment A Phases 2–3) and the node's LF/CRLF default are out of
   scope here and tracked separately.
10. **Transport is not papered over.** The SDK's tolerant raw transport exists
    only for genuinely unparseable servers; the node must still emit compliant
    HTTP (see RFC-062 and `docs/SDK_TODO.md`).

## 2. Motivation

The SDK and extension can run in two deployment modes:

- **Axia mode** — hosted relay/indexer over REST; unchanged by this RFC.
- **Hawk mode** — a paired local node reached over the node's RPC command
  surface.

A local node and the SDK are separate release artifacts. Without a pinned,
generated contract, any of the following silently drifts:

- a node renames or removes a command;
- a parameter becomes required (or stops being accepted);
- an enum gains/loses a value;
- the extension sends a parameter the node ignores;
- the SDK hardcodes a response shape that no longer matches.

The command set is large (132 commands across backup/base/mash/network/send/txn)
and several commands are destructive or administrative. The mapping therefore
needs to be explicit about *which* commands the wallet may use, not merely
"whatever the node accepts".

An external review of the C++ node also showed why conformance must be pinned:
small parsing/serialization differences produce different addresses, script
results or transaction IDs. The command contract is the boundary where such
differences are detected before they reach the wallet.

## 3. Scope and non-goals

**In scope**

- The command inventory and its generation/version pin.
- The parameter contract (names, required/optional, types, enums, ordering,
  unknown handling, value sanitation).
- The HTTP wire format and response envelope.
- The typed `MinimaRpcClient` surface.
- The `ChainStateProvider` → command mapping.
- Extension integration points that consume the provider.
- Error mapping and conformance tests.
- Known gaps and their owners.

**Non-goals**

- Changing node consensus, command semantics or response schemas.
- Provider routing, mode selection or fallback policy (RFC-062 Amendment A).
- Custody, signing policy or key handling (RFC-038, RFC-058, RFC-061).
- Omnia relay, P2P hub, lease and watermark transports (their own RFCs).
- The node MCP/tool surface (node RFC-0013) — commands are not MCP tools.
- Reimplementing the Axia indexer.
- Guaranteeing that every node command is safe for wallet use (see §8).

---

## 4. Definitions

- **Command surface** — the set of command names, parameters and enums the node
  advertises.
- **Command reference** — `COMMAND_REFERENCE.md`, generated from the node
  capability manifest by `tests/gen_command_reference`.
- **Generated metadata** — `MINIMA_COMMAND_PARAMS`, the TypeScript projection of
  the command reference.
- **Known command** — a command present in the generated metadata; its params
  are validated.
- **Unknown command** — a command absent from the generated metadata; usable only
  through `runCommand`, with explicit passthrough.
- **Provider method** — a `ChainStateProvider` operation the wallet calls.
- **Envelope** — the node's JSON response:
  `{ command, status, pending, response?, error? }`.
- **Pairing capability map** — the node-advertised endpoints/scopes stored by
  RFC-062; it decides *whether* a provider is available, not *which command* is
  used.

## 5. The contract

### 5.1 Source of truth and pinning

The chain is:

```text
node capability manifest (RFC-0011; `capabilities` command)
        ↓  tests/gen_command_reference
hawk-node/COMMAND_REFERENCE.md
        ↓  scripts/generate-minima-rpc-commands.mjs
packages/minima-rpc/src/commands.generated.ts
        ↓
packages/minima-rpc (validation + transport)
        ↓
packages/chain-provider (MinimaRpcProvider)
        ↓
extensions/totem-extension (resolveActiveChainProvider)
```

Rules:

- `COMMAND_REFERENCE.md` is generated; it is not hand-edited.
- `commands.generated.ts` is generated; it is not hand-edited.
- The generated header records the node identity it was produced from. The
  current pin is **`totem-node 1.0.100.0`, 132 commands**. (`1.0.100.0` is the
  node's Minima protocol version; the Totem Node product version is separate,
  e.g. `0.1.8`.)
- A node command-set change requires regenerating both artifacts and bumping the
  pin in the same change.

### 5.2 Generation pipeline

```bash
# node side (build-kat target)
build-kat/gen_command_reference COMMAND_REFERENCE.md

# SDK side
node scripts/generate-minima-rpc-commands.mjs ../hawk-node/COMMAND_REFERENCE.md
```

The generator parses the reference table and infers parameters from the
documented syntax:

| Reference form | Meaning | Generated type |
|---|---|---|
| `[name:value]` | required | inferred |
| `(name:value)` | optional | inferred |
| `name:true\|false` | boolean enum | `boolean` |
| `name:a\|b\|c` | string enum | `string` + `enum` |
| `name:{}` | JSON object | `object` |
| `name:[]` | JSON array | `array` |
| documented integer names (`height`, `max`, `offset`, …) | numeric | `number` |
| everything else | text | `string` |

Bare `name:value` tokens (e.g. `mashaddressinfo address:0x..`) are treated as
required. The generator preserves schema order; the transport emits parameters
in that order.

### 5.4 Parameter contract

The transport enforces the following before a request is sent:

1. **Command name shape.** `runCommand` accepts `[a-zA-Z0-9_-]+` only.
2. **Known command.** If the command exists in `MINIMA_COMMAND_PARAMS`, the
   supplied parameter names must be a subset of the schema. Unknown names are
   rejected.
3. **Required values.** Every `required: true` parameter must be present and
   non-null.
4. **Coercion.**
   - `boolean` accepts `true`/`false` (JS boolean or string).
   - `number` accepts a finite JS number or a numeric string; the emitted text
     must match `^-?\d+(?:\.\d+)?$`.
   - `object`/`array` are JSON-encoded.
   - `string` is `String(value)`.
5. **Enums.** If `enum` is set, the coerced text must be a member.
6. **Order.** Parameters are emitted in schema order, independent of object key
   order.
7. **Value sanitation.** A value may not contain whitespace or control
   characters (`[\x00-\x20\x7f]`), because the wire format is space-delimited.
   Rejecting is required; escaping is not permitted.
8. **Size bound.** A single parameter value is capped at **10 MiB**
   (`MAX_RPC_PARAM_LENGTH`). The node also caps the POST body (10 MiB in
   Hawk-node); because the body carries the command name and `name:` prefix, an
   at-cap value fails server-side rather than being silently truncated.

### 5.5 Wire format and response envelope

```http
POST http[s]://host:port
Content-Type: text/plain
Authorization: Basic base64(user:password)      # optional; default user "minima"

status
coins address:Mx... sendable:true
```

- The body is a single command line. Multi-command strings are a node concern
  and are not produced by the typed client.
- The response is JSON: `{ command, status, pending, response?, error? }`.
- `status: false` is an error; the transport throws `MinimaRpcError` with the
  node's `error` text.
- Read-only calls may opt into retries. Mutating calls are not retried on an
  ambiguous network failure.
- A tolerant raw transport exists for servers whose HTTP framing standard
  clients cannot parse. It is not a substitute for a compliant server; see §9.
- HTTPS is required for non-loopback hosts; plain `http` is accepted only for
  loopback (RFC-013 §11, RFC-062 §5).

### 5.6 Typed client surface

`createMinimaRpcClient(config)` exposes:

- `runCommand(cmd, params?)` — explicit passthrough.
- Read: `status`, `balance`, `coins`, `tokens`, `getAddress`, `newAddress`,
  `megammr`, `magic`, `history`, `burn`, `getTip` (`getchaintip`),
  `coinCheck`, `coinExport`, `mmrProof`, `verify`.
- Transaction builder: `txnCreate`, `txnBasics`, `txnInput`, `txnOutput`,
  `txnState`, `txnScript`, `txnSign`, `txnCheck`, `txnList`, `txnImport`,
  `txnExport`, `txnPost`, `txnMinePost`, `txnMine`, `txnDelete`, `txnClear`.
- Broadcast: `sendTransaction`.
- Diagnostics: `probeDeterministicAddress` (two `newaddress modifier:` calls).

`send` and `sendfrom` are also supported by the command builder, but the wallet's
Hawk path prefers the explicit transaction builder/broadcast methods so the
wallet owns coin selection and signing.

### 5.7 `ChainStateProvider` → command mapping

`packages/chain-provider/src/providers/minima-rpc.ts` is the normative mapping:

| Provider method | Node command(s) | Notes |
|---|---|---|
| `getCoins(query)` | `coins` | `relevant`, `sendable`, `coinid`, `address`, `tokenid`, `megammr`. |
| `getCoin(coinId)` | `coinexport` → fallback `coins` | `coins` only sees wallet-relevant coins; `coinexport` is the chain-level primitive. |
| `verifyDeposit(params)` | `coinexport` | Authoritative live check: existence, spent, owner, token, amount + proof. |
| `depositAddressFor(lp, opts)` | *(none)* | Deterministic address computation; no node call. |
| `getMmrRoot()` | `megammr` | Returns the advertised MegaMMR root/hash. |
| `getProof(coinId)` | `mmrproof` | Coin MMR proof. |
| `getMinTxPowWork()` | `magic` | `lastblock.currentmintxpowwork`; avoids hardcoding difficulty. |
| `getTip()` | `getchaintip` | The client's `getTip` maps to `getchaintip` (not `status`). |
| `getToken(tokenId)` | `tokens` | `tokens tokenid:`; throws when absent. |
| `searchTokens(query)` | `tokens` | Client-side filtering by name/creator, then offset/limit. |
| `getTokensByCreator(address)` | `tokens` | Delegates to `searchTokens`. |
| `submitTransaction(txBytes, witnessBytes, id)` | `txnmine` → `sendtransaction` | Serialises `TxnRow` (`MiniString(id) || Transaction || Witness`), asks the node to mine, then submits the mined TxPoW. |
| `broadcastTxPoW(txpowHex)` | `sendtransaction` | Submits a pre-mined TxPoW to the mempool. |

Invariants:

- `getCoin` must not silently treat a wallet `coins` miss as "not on chain"; it
  tries `coinexport` first.
- `submitTransaction` must preserve the `TxnRow` byte order; the node's
  `txnmine` builds the correct header (block number, difficulty, magic).
- `broadcastTxPoW` is for already-mined TxPoW; it is not a substitute for
  `submitTransaction`.
- Provider methods must not call admin/destructive commands outside this table.

### 5.8 Extension integration points

The extension consumes the contract in these places:

- `extensions/totem-extension/src/core/config/activeChainProvider.ts` resolves
  the provider from persisted config + consent; it returns `null` in Axia mode so
  existing Axia paths remain unchanged.
- `core/transaction/CoinSelectionService.ts` (`fetchSpendableCoins`) routes coin
  reads through `provider.getCoins`.
- `background/index.ts` uses the provider for `TOTEM_GET_CHAIN_TIP`
  (`provider.getTip`), `TOTEM_GET_COINS` (via coin selection), and Omnia relay
  chain access.
- `core/config/selfHosted.ts` persists `chain.mode`
  (`axia` | `minima-rpc` | `composite`) and the node URL/consent.
- The extension's dApp `RPC_COMMAND` handler keeps its own read-only allowlist;
  the full 132-command surface is not exposed to dApps.

Consent and identity are prerequisites: a persisted URL without consent fails
closed to Axia. Pairing identity/fingerprint verification is RFC-062, not this
RFC.

### 5.9 Error contract

- `MinimaRpcError` carries `command`, optional `minimaError` (the node's `error`
  string), and optional `httpStatus`.
- HTTP 401/403 → authentication error, never retried.
- HTTP non-2xx → HTTP error with status.
- `status: false` → command failed with the node's error text.
- Ambiguous network failure on a non-retryable command → immediate error (do not
  repeat a possibly non-idempotent operation).
- Parse failures on a JSON-looking body are surfaced, not silently coerced.

### 5.10 Unknown-command passthrough

`runCommand` is the only unknown-command path:

- The command name must match `[a-zA-Z0-9_-]+`.
- Parameter names must match the same shape.
- Values are sanitised as in §5.4.
- No schema validation, no enum/type coercion.

Typed client methods and provider methods must not use `runCommand` for mapped
operations. If a needed command is not generated, the correct change is to
regenerate the surface, not to add an ad-hoc passthrough.

### 5.11 Versioning and drift

- The generated header pins the source node version and command count.
- A change to command names/params/enums requires:
  1. regenerate `COMMAND_REFERENCE.md` from the node;
  2. regenerate `commands.generated.ts`;
  3. update the pin in the generated header (produced by the generator);
  4. run conformance tests;
  5. release the SDK with the change noted.
- A drift check fails CI when the generated file does not match the reference.
- Unknown/extra parameters are rejected, so a node-side rename cannot silently
  pass; it becomes a client-side error until the SDK is regenerated.

## 6. Normative invariants

1. `commands.generated.ts` is generated from the pinned `COMMAND_REFERENCE.md`.
2. No typed method sends a value containing whitespace or control characters.
3. No typed method sends an unknown parameter for a known command.
4. No typed method omits a required parameter.
5. Parameter order follows the generated schema.
6. Provider methods use only the commands in §5.7.
7. `getCoin`/`verifyDeposit` use `coinexport` for chain-level truth.
8. `submitTransaction` uses the `txnmine` + `sendtransaction` composition and
   preserves `TxnRow` ordering.
9. Mutating commands are not retried on ambiguous failures.
10. A non-compliant/unparseable server is a node defect, not a reason to add a
    standing tolerant path to the typed client.

## 7. Conformance and verification

**Generation/drift**

- `scripts/generate-minima-rpc-commands.mjs` must reproduce
  `commands.generated.ts` byte-for-byte from the pinned reference.
- The command count (132) and sentinel commands (`status`, `coins`,
  `coinexport`, `getchaintip`, `txnmine`, `sendtransaction`, `megammr`,
  `magic`) must be present.

**Transport**

- Missing required, unknown parameter, wrong boolean, non-finite number,
  out-of-enum and whitespace/control values all throw `MinimaRpcError` before
  the request.
- Schema order is preserved.
- 10 MiB bound is enforced.
- Response envelope mapping: `status:true` → `response`; `status:false` →
  error; HTTP 401/403 → auth error.

**Provider**

- Unit tests with a mock transport assert each method emits the expected command
  and parameters.
- `getCoin`/`verifyDeposit` prefer `coinexport` and fall back correctly.
- `submitTransaction` builds a `TxnRow` with `MiniString(id)` length-prefix,
  transaction and witness in that order.

**Extension**

- `provider-routing.test.ts` covers the RFC-062 capability routing logic.
- Coin selection and `TOTEM_GET_CHAIN_TIP` tests assert the provider is used when
  configured and consented, and Axia is used otherwise.
- Optional live-node integration tests run against a local Hawk node; they are
  not part of the default unit gate.

## 8. Security considerations

- **Command exposure.** The full surface is not a wallet API. Destructive/admin
  commands must remain behind the extension's own allowlist and the node's
  read-only RPC credential rules.
- **Injection.** Named parameters are space-delimited; whitespace/control
  characters are rejected to prevent parameter injection.
- **Credentials.** Basic auth is used over loopback or HTTPS only. Credentials
  never appear in URLs, logs or pairing invitations (RFC-062).
- **Payload size.** The 10 MiB client bound and the node's body cap prevent a
  single command from forcing unbounded allocation.
- **Key material.** Wallet-facing provider methods do not read or return private
  keys. The node's `keys` command is intentionally not part of the provider
  mapping; its `list`/`new` output must not include private keys (see the
  v0.5.5 hardening).
- **Node trust.** Pairing/pinning (RFC-062) establishes which node is being
  talked to. This RFC assumes that trust decision has already been made.
- **No fallback by default.** A missing capability is an error unless the user
  explicitly opts into Axia fallback (RFC-062 Amendment A).

## 10. Change control

- Any node command change starts at the capability manifest, not in the SDK.
- The generated reference and generated TypeScript are updated together and
  reviewed as a pair.
- The SDK release notes must state the pinned node version and the command-count
  delta.
- Removing/renaming a command is a breaking SDK change; deprecate first where
  feasible.
- This RFC becomes **Accepted** once the drift check is part of the default CI
  gate and the §9 routing/LF items are resolved or explicitly deferred.
